# StorageGRID Usage Proxy - Build and Validation Report

## Purpose

This document records the architecture, release model, and validation expectations for the StorageGRID Usage Proxy.

It is a build/release record, not the production operator procedure. For deployment, use `docs/SETUP_GUIDE.md`.

## Architecture

Runtime flow:

```text
HTTP-SNIFFER
    -> GET /storagegrid/usage
    -> X-StorageGRID-Proxy-Key
StorageGRID Usage Proxy
    -> GET /api/v4/org/usage with active bearer token
StorageGRID
    -> usage JSON
Proxy
    -> same successful usage response
HTTP-SNIFFER
    -> Splunk
```

Token lifecycle:

```text
startup
  -> POST /api/v4/authorize
  -> receive candidate token
  -> validate candidate with /api/v4/org/usage
  -> keep validated token in RAM

every configured refresh interval
  -> authorize candidate
  -> validate candidate
  -> replace active token only after validation

upstream HTTP 401
  -> reauthorize safely
  -> validate replacement
  -> retry usage once
```

The proxy does not persist the dynamic bearer token and does not modify or restart HTTP-SNIFFER during normal operation.

## Production deployment model

Docker is the recommended production deployment.

The production server runtime bundle is intentionally separate from the source repository:

```text
/mnt/storagegrid-usage-proxy/
├── compose.yml
├── proxy.env
└── certs/
    └── storagegrid-ca.pem
```

The image is built outside the closed network and transferred as:

```text
storagegrid-usage-proxy_<version>.tar
storagegrid-usage-proxy_<version>.tar.sha256
IMAGE_VERSION.txt                 # when generated by CI
```

The target server performs:

```text
SHA256 verification
    -> docker load
    -> docker compose up -d
```

No internal Docker registry is required for this deployment model.

## Production security model

Recommended listener configuration:

```ini
PROXY_BIND_HOST=0.0.0.0
PROXY_API_KEY=<configured>
ALLOW_UNAUTHENTICATED_NONLOOPBACK=false
```

Production therefore requires five environment-specific values:

```ini
STORAGEGRID_BASE_URL=
STORAGEGRID_USERNAME=
STORAGEGRID_ACCOUNT_ID=
STORAGEGRID_PASSWORD=
PROXY_API_KEY=
```

HTTP-SNIFFER uses the same shared key in:

```text
X-StorageGRID-Proxy-Key
```

TLS verification remains enabled:

```ini
TLS_VERIFY=true
CA_BUNDLE=/app/certs/storagegrid-ca.pem
```

The CA certificate is mounted read-only from the host `certs/` directory.

Container hardening retained in Compose:

```yaml
read_only: true
tmpfs:
  - /tmp
cap_drop:
  - ALL
security_opt:
  - no-new-privileges:true
```

## Release versioning

`TAG` remains the single source of truth for Docker release versioning.

For example:

```text
TAG = v1.1.0
```

should produce:

```text
storagegrid-usage-proxy:v1.1.0
storagegrid-usage-proxy:latest
storagegrid-usage-proxy_v1.1.0.tar
storagegrid-usage-proxy_v1.1.0.tar.sha256
IMAGE_VERSION.txt
```

The offline TAR should contain both the versioned image tag and `latest` so the production `compose.yml` does not need a version edit for every release.

## CI/CD model

Normal source changes should run the quality/test jobs.

A deployable image is produced only according to the repository release policy, using the value from `TAG`.

The project supports both GitHub Actions and GitLab CI. GitLab may route public Docker images through its Dependency Proxy or an approved registry mirror.

The source Dockerfile may use an overridable base image so GitHub/manual builds can use the normal public image while GitLab injects a dependency-proxy image reference.

## Required release validation

Before declaring a release production-ready, verify all applicable items:

- Python compilation passes.
- Python 3.6 compatibility validation passes if native compatibility remains supported.
- All shell syntax checks pass.
- `compose.yml` validates.
- GitHub workflow YAML validates.
- GitLab CI YAML validates.
- Complete automated test suite passes.
- `PROXY_API_KEY` is required for the intended non-loopback production listener.
- Config preflight and actual startup enforce the same listener-security rule.
- Docker image build succeeds.
- Version comes from `TAG`.
- Offline TAR contains the intended image tags.
- SHA256 file is generated.
- `IMAGE_VERSION.txt`, when produced, matches `TAG`.
- Real credentials are not baked into the Docker image.
- Private CA material is not baked into the Docker image.
- Dynamic StorageGRID bearer tokens are never persisted.

## Environment-dependent validation

These checks require the real closed-network environment and must not be claimed from source tests alone:

1. StorageGRID DNS/IP connectivity.
2. StorageGRID TLS trust using the approved CA certificate.
3. Real account ID, username, and password.
4. Successful `/api/v4/authorize`.
5. Candidate token validation through `/api/v4/org/usage`.
6. Proxy startup with production `PROXY_API_KEY`.
7. HTTP-SNIFFER reachability to the proxy on TCP `8787`.
8. HTTP-SNIFFER sends the correct `X-StorageGRID-Proxy-Key`.
9. `/storagegrid/usage` returns the expected live usage response.
10. Splunk receives the expected monitoring event.
11. Container recovery after server reboot behaves as expected.
12. Scheduled token refresh continues without HTTP-SNIFFER configuration edits or restarts.

## 9. Runtime API

Operator / HTTP-SNIFFER endpoint:

```text
GET http://<server>:8787/storagegrid/usage
```

StorageGRID endpoint used internally:

```text
GET /api/v4/org/usage
```

Authorization:

```text
POST /api/v4/authorize
```

The proxy does not require an application-level API key for the local network endpoint. The
approved closed network and host/network controls are the access boundary.

## 10. TLS

Normal production setting:

```ini
TLS_VERIFY=true
CA_BUNDLE=
```

If StorageGRID uses an internal CA that is not trusted by the Python runtime, provide the
approved CA PEM under `certs/` and configure `CA_BUNDLE` accordingly.

`TLS_VERIFY=false` is not the normal production configuration.

Docker Engine is not available in this execution environment, so `docker compose config`,

## 12. Final engineering decision

The project should remain intentionally small:

```text
HTTP-SNIFFER
      |
      v
StorageGRID Usage Proxy
      |
      v
StorageGRID Tenant API
```

No token-persistence mechanism, container restart automation, extra service, registry
deployment layer, Kubernetes layer, or application-level proxy API key is required for
the stated closed-network design.

The remaining unknowns are infrastructure facts, not reasons to invent application code:
the actual internal registry hostname/path and the GitLab Runner executor/configuration.
